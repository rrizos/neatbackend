neat backend · Lightsail eu-central-1 · 63.181.201.175

If the app gets slow or falls over

Work down this page in order. Every threshold here was measured on the box, not estimated — so "normal" below is genuinely normal.

Read this before you touch anything

Slow does not turn into down. Under a deliberate load test this box reached load 17.65 on 2 vCPU and still answered every single request — zero server errors — then returned to normal the moment the load stopped. It degrades by making people wait, not by falling over.

So the instinct to restart gunicorn because the app feels sluggish is wrong, and it makes things worse: you drop every request in flight, pay a cold start, and the traffic is still there when you come back. Restarting fixes a stuck process, not a busy one.

1

Open the health page

It does this entire triage for you and names the fix. Log in with your normal app admin account.

https://neatapp.gr/health

Read the word at the top. ok means the server is fine and the problem is somewhere else — the phone network, the app build, one user. Anything else, read the Do this list underneath: it is ordered by severity and every entry carries the exact command.

If the health page itself won't load, the box is not answering at all — skip to Service down.

2

Confirm it is really the server

Thirty seconds, from anywhere, no login:

curl -o /dev/null -w "%{time_total}\n" \
  -H "X-Neat-Client: 3" https://neatapp.gr/api/posts/

Under 0.30s — the server is healthy. Believe this over a complaint; the problem is on the reporting user's side.
0.3s to 2s — busy but serving. Real, not urgent.
Over 2s — genuinely saturated. Continue to step 3.

3

Find which one it is

Only one of these is usually true at a time. The health page tells you which; these are the same branches with the reasoning, if you'd rather look yourself.

Fix immediately

One IP is hammering you

Signature: load high, one address dominating the log, many requests to /api/posts/ with nc="-"

This is the most likely cause of a sudden slowdown and the cheapest to fix. The feed needs no login and has no rate limit, and a request without the app's header costs 980 KB and 0.335s against 13 KB and 0.031s for a normal one. Roughly six of those per second occupies both cores. One scraper is genuinely enough.

# who is it
sudo awk '{print $1}' /var/log/nginx/access.log \
  | sort | uniq -c | sort -rn | head -5

# block them — instant, and reversible with -D
sudo iptables -I INPUT -s THE_IP -j DROP

# undo later
sudo iptables -D INPUT -s THE_IP -j DROP
Ride it out

Real traffic, at the ceiling

Signature: load high, many different IPs, requests carrying nc="3"

The box tops out near 19 requests/second, and CPU is the only wall — memory and database connections were nowhere near their limits even at full saturation. There is nothing to fix in the moment. It stays up and gets slower; that is the designed behaviour.

If it stays there for hours rather than minutes, that is the case for resizing the instance — and it must add vCPU, not RAM. Do not attempt a resize during an incident: it is a snapshot-and-restore onto a new machine, it needs the nginx SSL key carried across by hand, and the static IP reattached.

Fix immediately

The disk is full

Signature: df -h / above 90%, uploads failing, possibly 500s

This is the only failure here that does not heal itself. When the disk fills, MySQL writes and nginx both stop, and nothing recovers until space exists. Normally 12% of 59 GB, so it takes something unusual — but check it first whenever things are broken rather than merely slow.

df -h /
du -sh ~/deploy-backups/*        # old deploy copies, safe to delete
sudo journalctl --vacuum-size=100M
Restart is correct here

Memory exhausted, or a stuck process

Signature: available memory under 200 MB, or swap in use, or high load with almost no requests arriving

This is the one case where restarting is the right move rather than the reflex. Normal is ~1,100 MB available and essentially zero swap — this box used 512 KB of its 2 GB in 43 days, so any real swap usage means something is wrong.

free -m
sudo systemctl restart gunicorn gunicorn-asgi
Fix immediately

The database stopped taking writes

Signature: nobody can post, sign up or send messages, but reading works

The health page reports three separate causes here, because the fix differs. Read-only means a failover left the instance half-switched — check it in the Lightsail console; nothing on the web server will fix it. Connections refused means the 61-connection ceiling was hit; restart gunicorn to drop stale connections. A long-running query holds locks and queues everything behind it — the page gives you the exact KILL line.

For reference, normal is 9–11 connections of 61, peak ever 23, and zero refusals — so this has never actually happened.

Not an outage

Uploads stuck on "processing"

Signature: health page shows the transcode queue backing up

Videos are encoded by a separate worker. If it wedges, uploads stay on "processing" but nothing else breaks — and posts still play, because a failed encode falls back to the original file.

Worth fixing promptly for a second reason: while anything is processing, every viewer looking at that feed re-requests it every 5 seconds, which roughly triples the load per user.

sudo systemctl restart neat-transcode
4

If nothing loads at all

Connection refused, 502, or a blank page. Check what is actually running before restarting anything — systemd already restarts these automatically (3 seconds for the web processes, 5 for the worker), so a service found dead usually means it is failing repeatedly rather than that it simply stopped.

ssh -i ~/Desktop/LightsailDefaultKey-eu-central-1-2.pem bitnami@63.181.201.175

systemctl is-active gunicorn gunicorn-asgi neat-transcode nginx redis-server
sudo journalctl -u gunicorn -n 100 --no-pager

sudo systemctl restart gunicorn gunicorn-asgi

If a service comes back and dies again within seconds, stop restarting it and read the journal — something in the code or config is wrong, and restarting in a loop only hides the message you need.

5

If the box is gone entirely

SSH times out, nothing responds, the Lightsail console shows the instance unhealthy. The database lives on a separate managed instance, so no user data is lost — only whatever photos and videos were uploaded since the last snapshot, because those sit on this disk and nothing backs them up.

Recovery is done entirely in the Lightsail console, with no shell:

1. Snapshots  →  create a new instance from the most recent one
2. Networking →  detach static IP 63.181.201.175 from the dead instance
3. Networking →  attach that same static IP to the new instance

The static IP is what carries neatapp.gr, so DNS needs no change and the certificate keeps working. Roughly ten minutes. Older installed app builds connect to that IP directly, which is the other reason it has to move rather than be replaced.

The short version

For whoever is covering while you're away

Site is slow

Do nothing. Report it. It will not fall over — it has been tested well past this and stayed up.

Site is fully down

Run one command:
sudo systemctl restart gunicorn gunicorn-asgi
Then say so.

Never do these

  • Don't restart because it feels slow. It drops live requests and the load returns immediately.
  • Don't deploy anything during an incident — and note the box cannot git pull at all: it has no GitHub credentials, so code only reaches it by file copy.
  • Don't run certbot --nginx. It rewrites the server blocks and breaks the bare-IP site that older app builds still depend on.
  • Don't resize the instance under pressure. It is a snapshot-and-restore onto a new machine; the nginx SSL key has to be carried over by hand or every older installed app stops connecting.
  • Don't delete anything under media/. Those files are the only copy — there is no backup and no object storage.
